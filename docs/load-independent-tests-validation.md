# PCの負荷で揺れるテストの修正

2026-10-22 / [Issue #47](https://github.com/Negi310/mission2026-game/issues/47)

[Issue #45の検証](https://github.com/Negi310/mission2026-game/pull/46)で、別のプロジェクトのUnityが同じPCで動いていた回だけ、`TankTownTests` の2件が失敗しました。重いフレームをわざと作って失敗を再現し、原因を確かめたうえで、実時間やフレームの長さに依存しない確認へ直しました。ゲームの動きは変えていません。

## 原因

|テスト|失敗の内容|原因|
|---|---|---|
|`ElevatedCannonLaunchesAlongTheVisibleBarrel`|発射の次のフレームで、砲弾の上昇量が0.0|砲弾は物理ではなく、`TankShell.Update` で `120m/秒 × Time.deltaTime` だけ進み、その区間に何かあれば爆発して消えます。テストの位置では、砲身の先10.96mに街灯があります。フレームが約0.091秒より長いと1回の移動が街灯に届き、砲弾は進まずに爆発します。`Destroy` はフレームの終わりまで遅れるため、テストは発射位置に残った砲弾を読んでいました。重いフレームは上限の0.333秒（約40m）まで伸びます|
|`PauseAndTimeoutFreezeGameplayAndRestartResetsCity`|再挑戦の1フレーム後の残り時間が59.46秒・59.38秒（期待は59.5〜60秒）|テストで開始演出を省く経路（`SkipIntroForTests`）では、街を作り終えた `Awake` の最後で時計が始まります。最初の `Update` までに、生成した部品の `Start` などが走ります。負荷のないPCでもこの間に0.39秒かかり、0.5秒の上限との差は0.11秒しかありませんでした|

同じ形の確認（再挑戦の1フレーム後に59.5〜60秒）が `TankTownGenerationTests.NormalRetryGeneratesANewCityAndOneMinuteEndsTheRound` にもあり、合わせて直しました。検証コピーを初めて開いた直後の実行では、ほかのUnityが動いていなくても、修正前のこの確認（59.37秒）と砲弾の確認（0.0）が失敗しました（`Logs/issue47-old-targets.xml`）。他の作業の負荷だけでなく、読み込み直後の重いフレームでも起きます。

砲弾は物理で動かないため、`WaitForFixedUpdate` で物理の更新を待っても直りません。

### ゲームの時計は変えない

- 時計が実時間で進むのは意図した仕様です。大型街は物理30Hz・追いつき最大0.1秒で、重いとゲーム内の時間が遅れるため、ゲーム内の時間で数えると60秒が伸びます（[大型街の軽量化の記録](large-stage-performance-validation.md)）。
- 通常の流れでは、3・2・1・GO!の後（`TankTownRoundFlow`）に時計が始まるので、ロードや最初のフレームの時間は数えません。GO!の時点で残り59.9〜60秒であることは `TankTownRoundFlowTests` が確かめています。最初のフレームの時間を数えるのは、テスト専用の経路だけです。

## 変更

- 砲弾: 発射の次の1フレームだけ、`Time.captureDeltaTime` で1フレームを1/60秒に固定し、終わったら0へ戻します。1回の移動は常に2.000mになり、上昇（0.14m）と砲身の向き（0.05度未満）の確認はそのままです。診断の撮影（`TankTown*Smoke`）と同じ方法です。
- 再挑戦（2件）: 「最初のフレームが0.5秒以内」の代わりに、減った時間（60 − 残り時間）が0以上で、再挑戦を頼んでからの実時間以下であること（60秒から数え直したこと）を確かめます。`TankTownTests` では、さらに実時間0.05秒後に残り時間が減っていること（すぐ時間が進むこと）を確かめます。
- 変更はテストだけです。ゲームの動き・設定・README、`Builds/` の実行版は変更していません。

## 検証

Unity 6000.3.19f1の独立した検証コピー（`D:\GitHub\mission2026-game-validation\issue-47`、`-batchmode -nographics`）で実施しました。PlayMode全体を全件成功で確かめるため、検証コピーには未マージのPR #46（1eff592）も入れています。PR #46はこの3つのテストに触れていません。

### 重いフレームの再現

検証コピーにだけ一時的なテスト（`TankTownLoadStallDiagnostics`）を置き、重いPCで起きる遅れを作りました。砲弾は、発射したフレームで0.4秒止めます。再挑戦は、新しい街の読み込み後に0.6秒かかる `Start` を1つ加えます。

|場面|1フレーム|移動量・減った時間|元の確認|新しい確認|
|---|---|---|---|---|
|砲弾・遅れなし|0.0191秒|2.290m（上昇0.160m）|成功|成功|
|砲弾・0.4秒の遅れ|0.3333秒|0.000m（街灯に当たって消える）|**失敗**（再現）|—|
|砲弾・0.4秒の遅れ・1/60秒に固定|0.0167秒|2.000m（上昇0.140m）|—|成功|
|再挑戦・遅れなし|—|0.391秒（実時間1.342秒）|成功|成功|
|再挑戦・0.6秒の遅れ|—|0.993秒（実時間1.950秒）|**失敗**（再現）|成功|

9件すべて成功しました（再現の2件は、元の確認が失敗することを確かめるテストです。`Logs/issue47-diag.xml`）。

### CPU負荷

論理CPU 8のPCで、CPUを使い続けるPythonのプロセス（通常の優先度）を同時に動かし、上の9件を3回実行しました。

|実行|負荷|結果|再挑戦・遅れなしで減った時間|砲弾・遅れなしの1フレーム|
|---|---|---|---|---|
|1|8プロセス（Unityの起動から）|9件成功|1.709秒|0.0305秒|
|2|8プロセス（Unityの起動から）|9件成功|3.944秒|0.0241秒|
|3|16プロセス（最初のテストから）|9件成功|1.817秒|0.0233秒|

負荷をかけると、わざと遅らせなくても再挑戦の最初のフレームで1.7〜3.9秒減り、元の確認（0.5秒以内）は、遅らせた場合も含めて6回すべてで失敗する値でした。新しい確認はすべて成功しています。砲弾の1フレームは、この3回では街灯に届く0.091秒を超えませんでしたが、超えた場合は上の再現のとおりです（`Logs/issue47-load-1.xml`〜`issue47-load-3.xml`）。

### PlayMode全体

一時的なテストを消してから実行しました。変更した2ファイルは、作業ブランチと検証コピーでSHA-256が一致しています。

- 負荷なし: 173件すべて成功（460.4秒、`Logs/issue47-playmode-full.xml`）。
- 8プロセスの負荷（最初のテストから）: 173件すべて成功（1135.0秒、`Logs/issue47-playmode-full-load.xml`）。全体が約2.5倍遅くなっても、ほかに失敗するテストはありませんでした。
